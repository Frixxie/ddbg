# Repository guidance

## Verification and fixtures

- Match CI: `cargo clippy --workspace --all-targets --locked -- -D warnings`, then `cargo test --workspace --locked`. Formatting: `cargo fmt --all -- --check` (apply with `cargo fmt --all`).
- Focused engine regression: `cargo test -p ddbg-core --test engine <filter> --locked`; this uses an in-memory fake DAP adapter, not LLDB. Driver equivalent: `cargo test -p ddbg-driver --test fake_adapter <filter> --locked`.
- Real-adapter suites are ignored by default: `cargo test -p ddbg-core -p ddbg-driver -p ddbg-mcp --locked -- --ignored`. They build their fixtures themselves. Require `lldb-dap`, `make`/a C compiler (`cc` for MCP); Python cases use `$DDBG_PYTHON` (default `python3`) and silently pass after printing a skip if `debugpy` cannot be imported.
- Ordinary `ddbg-test` integration tests build and run fixture projects. The .NET case requires SDK 10 (`net10.0`, xUnit v3/Microsoft.Testing.Platform); CI installs it, but local tests skip when `dotnet` is absent. An installed older SDK does not trigger that skip.
- `fixtures/` is excluded from the workspace. Build a fixture via its own manifest, e.g. `cargo build --manifest-path fixtures/hello-rust/Cargo.toml`; its executable is under `fixtures/hello-rust/target/`, not the root `target/`.
- Fixtures deliberately contain failing tests; provider tests assert those failures. Debugger tests also hard-code fixture source line numbers, so coordinate fixture edits with assertions in `lib/ddbg-{core,driver,mcp}/tests/`.

## Wiring and invariants

- `bin/ddbg/src/main.rs` selects REPL, TUI, or MCP. Despite its name, `ddbg-cli` also owns shared startup (`prepare`), parsing, rendering, and command dispatch (`Session::execute`); TUI and driver reuse it, and MCP wraps the driver.
- Test commands are handled in `lib/ddbg-cli/src/session.rs`, not by the engine. Providers in `ddbg-test` discover/run tests and produce `DebugTarget`s; project detection lives in `ddbg-project`. Neither providers nor frontends talk directly to DAP.
- `lib/ddbg-core/src/engine.rs` is the single owner of session state; clients send `Command`s through `EngineHandle` and subscribe to `DebugEvent`s. Protocol framing/transport is in `ddbg-dap`; adapter-specific launch arguments belong in `lib/ddbg-core/src/adapter.rs`.
- Generic DAP features are gated by negotiated capabilities, not adapter names. DAP breakpoint updates replace the complete set (per file for source breakpoints, globally for function breakpoints), never just the new breakpoint.
- Frame/scope/variable references and watch values are invalid after resume. Preserve `DebugSession::on_resume` invalidation; desired breakpoints and watch expressions survive restarts.
- MCP must keep `pause`, `kill`, and `end_session` usable while a resume/wait call holds the session lock; its separate engine handle is intentional. Keep stdout reserved for MCP transport; logging is file-based (`DDBG_LOG`, `--log-dap`).
- `DESIGN.md` is a draft containing unimplemented proposals (e.g. `.ddbg.toml`) and stale milestones. Verify behavior against code and `README.md`, rather than implementing the draft as if it were current configuration.

## Release maintenance

- `.github/workflows/release.yml` is generated by cargo-dist 0.32.0. Change `[workspace.metadata.dist]` in `Cargo.toml`, then run `dist generate`; do not hand-edit the workflow.
- Workspace crates are versioned together; internal path dependency versions are also in root `Cargo.toml`. `scripts/release.sh [version]` updates these and `Cargo.lock`, generates `CHANGELOG.md` with git-cliff, tests, and **commits with jj**; it only prints publish/push/tag steps. Do not use it as a harmless version-check command.
- Conventional Commit prefixes drive git-cliff version bumps (`cliff.toml`): before 1.0, features/breaking changes bump minor, other changes bump patch.
